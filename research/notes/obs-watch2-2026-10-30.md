## Q12: installing a watch app, and `isWatchAppInstalled` (level 3)

- `simctl install <phone> WCP2.app` (iOS app with the watch app embedded
  at `WCP2.app/Watch/WCP2Watch.app`), both devices booted, the pair fresh:
  the phone's appconduitd added the watch app ("new and user says install
  all apps so installing"), created a unique install ID, and started an
  install operation over IDS service `…appsyncconduit.v2`. The transfer
  itself uses a **Unix-domain socket**: the watch's appconduitd created a
  listening socket at `/tmp/appconduit_<stream UUID>.sock` and answered
  with its path; the phone's appconduitd connected to that path ("Socket
  setup successful", "Sending Hello"). This works on the Mac only because
  both simulators' processes share the host's `/tmp`.
- The watch then refused the install: its install receiver asked for free
  space, got **0 bytes** (the cache-delete client logged "unable to stat
  volume: /private/var/mobile"), asked the cache-delete daemon to purge
  12 288 bytes, waited while every purge service answered or timed out
  (several "failed to respond after 90 seconds"), purged 0 bytes, and
  10 min after the request answered the phone with error 12 ("Need 12288
  bytes … but only have 0 bytes", "Canceling coordinator … due to internal
  error"). The phone logged "Got error 12 in hello response from remote
  side", "Failed to install app". **Installing through the phone does not
  work in the reference simulator** (the watch app never appeared on the
  watch). Round 0's failure (no registered `appsyncconduit.v2` receiver)
  was load; this is the real end.
- `simctl install <watch> WCP2Watch.app` (direct): installed in 2.4 s. The
  watch's appconduitd noticed the new app and **sent the phone an install
  notification** ("Sending message to companion noting installed apps",
  service `…appsyncconduit.v2`); 0.7 s later the phone's appconduitd "Setting
  state to installed for dev.ycode.wcp2.watchkitapp", posted its
  applications-updated notification, and the running phone app got
  `sessionWatchStateDidChange` with **`isWatchAppInstalled` true** and
  `watchDirectoryURL` =
  `<phone app data container>/Library/Application Support/com.apple.watchconnectivity/<watch UDID>/WatchContent/<install ID>`
  (the install ID in upper-case hex, the one the phone's appconduitd had
  created for the failed install). wcd learns the state from appconduitd
  (`enumerateLocallyAvailableApplicationsForDeviceWithPairingID…`).
  So the reference reports true after a direct install once the pairing
  is healthy; round 0's false came from the watch's appconduitd not yet
  receiving under load. Ycode's true (W5 r2, r3) matches.
- Precondition seen: the iOS companion app was installed on the phone
  before the watch app was installed on the watch. (Not tested: the
  reverse order.)
- `xcodebuild -showdestinations` for a hand-written project with an iOS app
  target and a single-target watch app embedded in it ("Embed Watch
  Content", `$(CONTENTS_FOLDER_PATH)/Watch`): the **watch scheme lists**
  every watchOS 27 simulator **and every iOS simulator that has an active
  paired watchOS 27 simulator** (here iPhone 17, iPhone 17 Pro Max, iPhone
  Air of the owner's default set and `ycode-test-phone2-a`); phones whose
  watch runs 26.5 are listed as incompatible. `xcodebuild build -destination
  'platform=iOS Simulator,id=<that phone>'` for the watch scheme fails
  ("Unable to find a device matching the provided destination specifier"):
  the paired-phone destination exists for the IDE's run, not for
  `xcodebuild build`.
- Level 4 (IDEiOSSupportCore strings, needed to name Xcode's install
  path): an install option key `SkipWatchAppInstall` (also in CoreSimulator
  and in CoreSimulatorBridge, which sets it on its install request), the
  worker method name `_willInstallWatchAppForCompanion:maxTries:`, the
  errors "The install is directed to a paired Apple Watch, but there isn't
  one." and "Select an iPhone Run Destination with a paired Apple Watch.",
  and a "proxied device" set per companion (active proxied device). Read
  together with the destinations above: Xcode runs a watch app on a
  destination that names the phone, finds the phone's active paired watch,
  and installs the watch app on that watch; the iOS app's own install can
  be told to skip the embedded watch app. Which install call Xcode uses for
  the watch was not observed (no GUI run).

## Q11: `transferUserInfo` (level 3)

- Sender: `WCSession` writes each user info to
  `<sender app data>/Library/Application Support/com.apple.watchconnectivity/<peer UDID>/UserInfoTransfers/<transfer UUID>/userinfo-transfer-wire-data`
  (83 bytes for our three-key dictionary) and hands it to wcd; wcd sends it
  as an **IDS resource** (`sendResourceAtURL`): it copies the file to
  `DEV/data/tmp/` and ids_simd sends one MIG 1000 request whose IDS data is
  3 381 bytes (message id = the transfer UUID). The sender gets
  `didFinish userInfoTransfer` with no error 35–45 ms after the call.
- Receiver: ids_simd applies its link delay, writes the resource into the
  **receiving device's** `DEV/data/tmp/<UUID>/userinfo-transfer-wire-data`
  (sometimes with a random suffix) and hands the message to wcd ("was
  handled"). In wcd the IDS framework logs "incomingMessage on connection
  …" and offers it to wcd's delegate as an incoming *message*
  ("doesRespondToSelector? NO" for both the plain and the with-context
  form). wcd never logs the transfer; nothing is written to the receiving
  app's `Documents/Inbox/com.apple.watchconnectivity/<peer>/UserInfo/`
  (the receiving `WCSession` reads `contents.index` there and finds
  nothing). **`session(_:didReceiveUserInfo:)` is never called in the
  reference either**: watch → phone with the phone app in the foreground
  (3 transfers, 2 min), phone → watch with the watch app in the foreground
  (2 transfers), watch → phone with the phone app not running and launched
  3.5 min later (`hasContentPending` true at activation, nothing
  delivered). No other daemon and no app launch is involved.
- Contrast, delivered: application context (a protobuf message, type 3)
  reaches a running app and, for an app that was not running, is delivered
  at its next activation (`didReceiveApplicationContext` twice on launch).
  **`transferCurrentComplicationUserInfo`** (phone → watch) *is* delivered:
  wcd sends a protobuf message of type 9 ("UserInfoComplication", 84-byte
  payload) plus a resource with a fixed identifier; the receiving wcd
  persists it as
  `<watch app data>/Documents/Inbox/com.apple.watchconnectivity/<phone UDID>/UserInfo/complication-userinfo-id`
  (+ `contents.index`), pings the client, and the running watch app got
  `didReceiveUserInfo` (12 s after the send, queued behind a 1 MB file in
  ids_simd's delay; `isComplicationEnabled` false, remaining transfers 50
  unchanged).
- So Ycode's W5 result (senders finish, receivers' wcd get the IDS message,
  apps get nothing) **is the reference behavior**.

## Q5: `transferFile` (level 3)

- Sender: `transferFile` finishes (`didFinish fileTransfer`, no error)
  36 ms (1 KiB), 0.52 s (1 MiB) and 0.1 s (20 MiB) after the call. wcd
  sends the file **inline** as one IDS resource: ids_simd data of 7 087 B
  (4 KiB file), 1 051 958 B (1 MiB), **20 974 907 B (20 MiB)** — the file
  size plus about 3.4 KB of envelope. One MIG 1000 request per file.
- Receiver: ids_simd writes the file at once into the receiving device's
  `DEV/data/tmp/<UUID>/<sender's file name>`, then delays delivery by its
  link model: 10.45 s for 1 MiB, **205.6 s for 20 MiB** (0.175 s + 10 µs per
  byte), and later messages to the same device wait behind it (the
  complication user info above took 12 s). Then exactly as user info: wcd
  is offered an incoming message it does not handle; **the receiving app
  never gets `session(_:didReceive:)`**; the receiving app's container gets
  no `Documents/Inbox/…/Files`.
- In this run ids_simd read `SimulatedNetworkRestrictions-AllServices` = 1
  and had no per-service key for `watchconnectivity`, so WatchConnectivity
  traffic **was** delayed (round 0 saw it off). The switch is the guest's
  preference, set by the peer at pairing.

## Q9: unpair, remove-unpaired, switching (levels 3 and 4)

Sequence run (times on the Mac clock; the phone stayed booted until the
last step):

1. Fresh pair phone + watch A, both booted: both bridges connect, then
   set-active "has not previously paired. Pairing."; the watch's bridge
   first waits for data migration (it polls the migrator's plug-in results
   about once a second; 12 s). nanoregistryd's transaction log names the
   XPC method behind the bridge's `pairWithSimulator:…`:
   `xpcPairWithSimulator:withCompletion:`; the registry clients' reads are
   `xpcGetDeviceCollectionWithBlock:` and
   `xpcGetDiffSinceTokenValue:getSecureProperties:withBlock:`.
2. Watch A shut down: the phone's bridge got **"disconnect from remote A"**
   (round 0 thought the survivor gets nothing).
3. `simctl pair watchB phone` (inactive), then `simctl pair_activate` of it
   with the phone up and watch B down: the phone's bridge got set-active
   for B at once, "has not previously paired. Pairing.",
   `xpcPairWithSimulator`, Add/Switch in ids_simd, then property requests
   to an unreachable peer, retried. `pair_activate` did not return;
   `device_set.plist` showed both pairs inactive. After 4 min 27 s the
   registry gave up: `com.apple.nanoregistry.pairingerror` 13 "IDS connect
   timeout", record `[DELETED]`, the bridge logged
   `ids_relay_set_active:217 : <that error>`; `pair_activate` returned 0 and
   the pair became active. Booting watch B: the host sent connect and
   set-active to both; pairing succeeded in 24 s.
4. Watch B shut down 15 s later: "disconnect from remote B" on the phone,
   and the phone's registry **deleted B** ("property request failed …
   failed after retries" from the first attempt's leftovers, then
   `[DELETED]`).
5. `pair_activate` of pair A (A shut down, previously paired): phone bridge
   "has previously paired.  Switching." → `xpcSwitchToSimulator:withCompletion:`
   → `IDSSimulatorLocalPairingSwitchActivePairedDevice(A)`; done in 16 ms;
   `pair_activate` returned in 0.18 s. (`xpcSwitchIndex:` calls follow from
   other clients.)
6. Boot A: both bridges connect and set-active; the watch's bridge logged
   `ids_relay_set_active:181 : NSPOSIXErrorDomain 37 "Operation already in
   progress"` (the phone was already its active device); the phone's bridge
   logged nothing after the request (A was already active there). The pair
   showed "(active, connected)". Remove-unpaired on the watch: host
   [phone], sim [phone], unpair [].
7. `simctl unpair` of pair A, both booted (0.26 s): phone bridge "unpair
   from remote A" → `xpcUnpairWithSimulator:withCompletion:` →
   `IDSSimulatorLocalPairingDeletePairedDevice(A)` → ids_simd
   `deletePairedDeviceWithSimulatorID:completion:` → `isPaired` 0 →
   `[DELETED]` 2.2 s later → completion → "disconnect from remote A". A
   shut down and its `data` was recreated.
8. Pair A again (same UDID, erased) and boot it: phone "has not previously
   paired. Pairing.", both completions without error within 65 s; after a
   direct install of the watch app the phone app reported
   `isWatchAppInstalled` true. (The watch app's `activateSession` had not
   completed 30 s after its launch on this freshly paired watch — the
   round-0 Q8 effect; not followed further.)
9. Both shut down; `simctl unpair` of that pair (A erased again); phone
   booted alone: its bridge's remove-unpaired logged host [B] (the other,
   inactive pair), sim [A], unpair [A], and nanoregistryd ran
   `xpcUnpairWithSimulator` → DeletePairedDevice(A) → `[DELETED]` 14 s
   after the request.

## W3a: input on the watch (levels 3 and 4)

- **dtuhidd is active on the watch.** CoreSimulator's `dtuhidd` (job
  `com.apple.coredevice.dtuhidd`) was running and the notify state
  `com.apple.coredevice.dtuhidd.active` was 1 (the host's CoreDevice lists
  every booted simulator as "connected"; `devicectl list devices` shows
  them "simulated"). While it is 1, backboardd's SimulatorHID bundle keeps
  its buttons, keyboard and touch services disconnected
  ("dtuhidd-suppressed").
- **Legacy Indigo messages for buttons, keys and touches have no effect.**
  Home (source 0), lock (1), side (3000), a key (usage 4) and taps through
  `SimDeviceLegacyHIDClient`: backboardd logs "Connecting dtuhidd-suppressed
  service due to IndigoHID event" for the service, the HID event system logs
  "Service added" and **"Service removed"** for it in the same millisecond,
  and no event reaches backboardd's routing (no sender, no destinations,
  no UIKit event in Carousel). Setting the notify state to 0 by hand
  ("dtuhidd state changed to inactive") did not bring them back. So on
  Xcode 27.1 the watch's buttons and touches come through dtuhidd (Device
  Hub's path), which this round did not drive (no GUI; its XPC payload is
  not documented). The **crown press, side button and Action button**
  usages and effects therefore remain open (Q2, Q3).
- **Crown rotation works through Indigo** (the crown service is not in the
  suppressed set). Each `IndigoHIDMessageForDigitalCrownEvent(double)`
  becomes one event from sender `0xACEFADE00000001`
  (`MainScreenDigitalCrownService`), which backboardd routes as a **Scroll**
  event to the keyboard-focus context (Carousel's main UI; the frontmost
  app's window when an app is in front); UIKit delivers it as a scroll
  `UIEvent` (type 7, subtypes 200 and 201) and Carousel handles it as a
  wheel event (`_wheelChanged`, the active controller's crown input
  handler). AttentionAwareness gets a "DigitalCrown" attention event
  (backlight idle timer, watchgesturesd).
- Crown effects: on the face, **positive deltas** start the transition
  face → Smart Stack ("New range transitioningSmartStack", "apply state:
  clock → interactiveClockToSmartStack, method: crown"), **negative**
  start face → Notification Center ("transitioningNotificationCenter").
  Our bursts (up to 30 events × 20 or 20 × 50 at 16 ms) moved the
  sequencer offset to at most 0.0075–0.014 and it sprang back to the face
  when the events stopped (the transition did not complete). In an app
  (watch Settings) positive deltas scroll the list **forward** (towards the
  end), negative back; 30 × 20 scrolled from the top to the end of the
  list. The unit is not a pixel: 10 × 0.1 and 10 × 1.0 barely moved the
  face sequencer; Ycode should keep the host's value as the event's delta
  and treat detents as the guest's business.
- **Watch gestures work through Indigo**, by another path:
  `IndigoHIDMessageForWatchGesture(uint32 type)` → the SimulatorHID bundle
  in backboardd (`handleGestureType:`) → XPC to watchgesturesd's
  `com.apple.WatchGestures.WatchGesturesSimulatorServer` →
  `WAGSimulatorSessionManager handleSimulatorGestureType:<n>` →
  watchgesturesd's own HID service (sender `0x100E229500000`) dispatches a
  **GenericGesture** event that backboardd sends to the keyboard focus.
  Numbering: **0 = double tap** (GestureType HandTap; on the face it opened
  the Smart Stack — Carousel's primary-action interaction), **1 = flick**
  (GestureType HandFlick; dismissed the Smart Stack back to the face
  through ClockFace's dismiss interaction), **2 = single tap** (accepted,
  then "Grey event rejected (no receiver)"), **3, 4, 5**: logged as
  received, no handler. The second argument of our builder call is unused
  (the builder takes one `uint32_t`).
- Level 4 (SimulatorKit strings, Swift/ObjC type metadata): the builder
  signatures `IndigoHIDMessageForDigitalCrownEvent(double)` and
  `IndigoHIDMessageForWatchGesture(uint32_t)`; the Indigo event union has a
  `_watch_gesture_event` member of two 32-bit fields; the watch SimulatorHID
  bundle names `MainScreenDigitalCrownService` and `handleGestureType:`;
  dtuhidd names `IndigoButtonEvent`, `IndigoKeyboardButtonEvent`,
  `LegacyHIDUsagePair` and "No main screen button service found for button
  event".
- No guest-side HID monitor was tried: `hid-input.md` records that an
  ad-hoc probe cannot get HID client entitlements; backboardd's and the
  apps' own logs were enough for what reached the guest.

# OBS-WATCH3 observations (agent OBS-WATCH3, 2026-10-31)

Dirty-room notes behind the additions to `specs/simulator/device-pairing.md`
§14 (Q13, Q14), `specs/simulator/watchos.md` §5.2 (Q2, Q3, Q15) and
`specs/simulator/health-simulation.md` §12 (open questions 9 and 11). Prose
only. Raw logs, screenshots, store copies and string lists stay in
`research/dirty/watch3/` (git-ignored). No disassembly or decompilation;
Ghidra and the reference tools folder were not opened. Bundle metadata
(level 4) was limited to string searches in Xcode's frameworks, CoreDevice
and one pass over the watchOS runtime's shared cache for button names.

Our code: the earlier probes `WCProbe2` and `HealthSim` (rebuilt; a copy of
HealthSim with the bundle ids `dev.ycode.hs3` / `dev.ycode.hs3.watchkitapp`
for a fresh HealthKit identity), the hand-written two-target project of
OBS-WATCH2 for `xcodebuild`, the Mac-side `watchhid` and `hidsend`, and three
new small tools kept with the samples outside the repository: `watchhid3`
(adds an arbitrary-usage sender with a chosen target and a usage scan),
`gestprobe` and `gestfields` (run inside the watch with `simctl spawn`:
they call the exported IOKit constructor of a GenericGesture event with
chosen values and print the event's own description; nothing is
dispatched).

## Setup

- Xcode 27.1, CoreSimulator 1174.9.2. Devices created for this round only:
  `ycode-test-phone3-a` (iPhone 18 Pro, iOS 27.0 24A434),
  `ycode-test-watch3-a` (Apple Watch Series 12 46mm, watchOS 27.0 24R362),
  `ycode-test-watch3-b` (Apple Watch Ultra 4 49mm, watchOS 27.0). All were
  shut down, unpaired and deleted at the end; `device_set.plist` was
  byte-identical before and after.
- At most one phone and one watch booted at a time. Host load 12–340
  (other agents' builds); times are upper bounds.
- **dtuhidd off in our test watches.** In each test watch we ran
  `launchctl disable system/com.apple.coredevice.dtuhidd` and rebooted it:
  the job (demand-launched by its Mach services) then never starts, the
  notify state `com.apple.coredevice.dtuhidd.active` stays 0 from boot, and
  the SimulatorHID bundle never suppresses its buttons, keyboard and touch
  services. Legacy Indigo buttons and touches then work through
  `SimDeviceLegacyHIDClient` (OBS-WATCH2 had set the state to 0 by hand
  while dtuhidd ran, which did not help). The override lives in the
  device's data and went with the device.
- Logs: `simctl spawn … log stream --level debug` per device, with debug
  enabled for `com.apple.BackBoard`, `com.apple.iohid`, `com.apple.Carousel`,
  `com.apple.UIKit`, `com.apple.wcd`, `com.apple.IDS_SIMD`, `com.apple.IDS`,
  `com.apple.paireddeviceregistry`, `com.apple.HealthKit` in those guests.
- No GUI was used: every tap and button was our own Indigo message to our
  own test device. The owner's Device Hub and simulators were not touched.
- Incident (not ours): at 01:12:16 the host's `SimLaunchHost-arm64` died
  (bus error inside dyld while unloading an image; load average 270–340);
  every booted simulator on the Mac shut down, ours included. We rebooted
  ours and repeated the step that was running.

## Q3 (watchOS Q2, Q3): buttons on the watch (level 3; usage pairs level 2)

With dtuhidd off, `IndigoHIDMessageForButton(source, down/up, target 0x33)`
reached backboardd from the buttons service (sender `0xACEFADE00000000`).
backboardd logs each as `<name> page:<p> usage:<u>` and routes it to the
system app (Carousel), which logs its own key name:

| Indigo source | HID usage (page/usage) | backboardd name | Carousel | Effect seen |
|---|---|---|---|---|
| 0 | 0x0C / 0x40 | Home | `crown` | tap on the face: **app grid** (Launcher); tap in an app: back to the **face**; held 1.8 s: "Crown held" → Siri presented, dismissed on release |
| 1 | 0x0C / 0x30 | Lock | `power` | "Power button tapped, toggling screen state" (screen off / on) |
| 3000 | 0x0C / 0x95 | Side | `pill` (mask "button") | tap: **Control Center**; held 2.5 s ("held", then "long held"): the **power-off / Emergency SOS** sheet (Cancel, power icon, SOS slider) |
| 500 | 0x0C / 0x1BA | DigitalWallet | — | no destination |
| 2000 | 0x0C / 0x223 | ACHome | "Unknown button" | none |
| 10000 | keyboard page 7 / usage 0 | KeyPress | "Unknown button" | none |
| 2–8, 1000, 4000 | vendor-defined event 0xFF00 / 0x10 | — | — | none |
| 0x400002 | — | — | — | **backboardd crashed** (in the HID bundle, while making a vendor-defined event); the whole watch UI restarted |

The **Action button** (Ultra) has no Indigo button source. Its usage pair is
in the device chrome Xcode uses for the type: the Ultra 4's
`chromeIdentifier` is `com.apple.dt.devicekit.chrome.watch6`, whose
`chrome.json` lists three inputs: `digital-crown` (type crown, 0x0C/0x40),
`side-button` (type button, 0x0C/0x95) and **`left-side-button`**
("Left Side", type button, page **0xFF01**, usage **0x200**); the Series 12's
`watch5b` has only the first two. Of the nine watch chromes only `watch4`
(Ultra, Ultra 2) and `watch6` (Ultra 3, Ultra 4) have the third input, with
the same pair. `IndigoHIDMessageForHIDArbitrary` with
target 0x33 and that pair produced backboardd's "Action page:0xFF01
usage:0x200" and Carousel's key **`sting`**; with no action chosen the watch
showed "Choose what you'd like the Action button to do." with a **Choose
Action** button and Cancel. (backboardd also names 0x0B/0x2D "Action", but
Carousel treats that pair as unknown.) A scan of the consumer page
0x00–0x3FF and the telephony page 0x00–0xFF through the same path found no
other pair Carousel knows except 0x0C/0xCF (VoiceCommand → Carousel `siri`).

Target 0x33 of the arbitrary builder lands on the buttons service; target
0x32 lands on the touch service (sender `…06`); backboardd routes a known
button pair whichever service sends it. Legacy taps (`hidsend tap`) also
worked with dtuhidd off (the Action sheet's Cancel dismissed it).

## Q3 (watchOS Q15): watch gestures (level 3; constructor level 1)

Gesture 0 (double tap) and 1 (flick) went, as OBS-WATCH2 saw, from the
bundle to watchgesturesd's simulator server ("_queue_setupConnectionIfNeeded",
"handleSimulatorGestureType:0"). watchgesturesd's debug log prints the HID
event it then dispatches:

| | double tap (0) | flick (1) |
|---|---|---|
| EventType | GenericGesture | GenericGesture |
| GestureType | HandTap | HandFlick |
| Count | 2 | (absent) |
| Phase | Ended | Ended |
| ValueType | Relative | Relative |
| Flags | 0x4000000 | 0x4000000 |
| UIKit event in the focused app | type 15, subtype 220 | type 15, subtype 221 |

It comes from watchgesturesd's own HID service, whose primary page and
usage are 0 (backboardd: "unknown senderID … strangeness: primary page is
zero") and is still routed to the keyboard focus. Single tap (2) is
rejected inside watchgesturesd ("no receiver"); nothing is dispatched.

Numbers: `gestprobe` called the exported constructor of a GenericGesture
event (allocator, timestamp, gesture type, options) inside the watch with
the values 0–12 and printed each event's description: **0 Tap, 1 Swipe,
2 HandTap, 3 unknown, 4 HandTapHold, 5 Squeeze, 6 LongSqueeze,
7 DoubleSqueeze, 8 HandFlick**, 9–12 unknown. `gestfields` read the event's
integer fields: the event type is **39**; field (39 << 16 | 0) holds the
gesture type, and setting field (39 << 16 | 1) is what the description
prints as **Count**. The XPC message between the bundle and watchgesturesd
was not recorded (not needed to make the event).

The crown rotation event's axis (watchos.md Q16) is not printed by any log
we enabled; still open.

## Q1 (pairing Q13): WatchConnectivity after a switch (level 3)

Phone app `WCP2` running in the foreground throughout; watch app installed
directly on each watch.

1. **Baseline**: phone + A, the phone app activated, `isPaired` and
   `isWatchAppInstalled` true, `watchDirectoryURL` under A's UDID,
   reachable.
2. **Switch to a never-paired watch** (A shut down; `simctl pair B phone`
   inactive; B booted; `pair_activate` of B's pair, 1.6 s, "has not
   previously paired. Pairing."). Phone wcd: device became inactive and
   active notifications → "Resetting initial state" → "Handling switch with
   nil pairing ID" → "No matching NRDevice for active IDS device"; 0.8 s
   later wcd was launched for the NanoRegistry **device-did-pair** event →
   handles the switch → "systemObserverActiveDeviceSwitchStarted" → set up
   initial state ("isPaired: YES, pairingID: B") → the client is
   re-activated "for currently active counterpart; awaiting initial set up
   complete". The app got **`sessionDidBecomeInactive` and
   `sessionDidDeactivate` in the same millisecond** (it calls `activate()`
   again from the latter). The set-up then failed: the phone's appconduitd
   had no IDS device for B ("No IDS Device registered with identifier B",
   wcd: ACX error 28, "initial set up failed. Awaiting trigger"); the app's
   session stayed **not activated** for 5 min, a relaunch did not help, a
   direct install of the watch app on B did not help. On B the watch app
   activated, `isCompanionAppInstalled` true, reachable true.
3. After a **phone reboot** with A active again, the app activated with A
   (76 s under load).
4. **Switch to a previously paired watch** (A shut down; B booted;
   `pair_activate` of B's pair, 0.33 s, "has previously paired.
   Switching."; nanoregistryd: A `isActive` 0, ids_simd
   switch-active-paired-device to B, B `isActive` 1, the
   `watchdidbecomeactive` notify state 1 then 2). Phone wcd: the same five
   lines as in step 2 ending in **"No matching NRDevice for active IDS
   device" — and nothing more**. No device-did-pair event comes for a
   device that is already paired. For 3 min the app got **no callback**;
   it kept `activationState` 2, `isPaired` true, `isWatchAppInstalled`
   true, `watchDirectoryURL` under **A's** UDID, not reachable. A relaunched
   phone app logged in wcd "client pairingID: (null), system pairingID:
   (null) … awaiting initial set up complete" and never activated.
5. **Phone reboot** with B active: the app activated with B
   (`watchDirectoryURL` under B's UDID, `isWatchAppInstalled` true once the
   watch state arrived).

So the reference's phone WatchConnectivity does not follow a switch to a
watch paired before; Ycode's logs ("Handling switch with nil pairing ID",
"No matching NRDevice for active IDS device", the session left with the old
watch) are the reference's behavior. It follows a switch to a newly paired
watch through the device-did-pair event, and it starts with whatever watch
is active when wcd starts.

## Q4 (health open question 9): a watch app's HealthKit authorization (level 3)

HealthSim's watch app (`dev.ycode.hs.watchkitapp`, companion `dev.ycode.hs`)
asked for 7 types (share and read):

- At the request, before any answer, the watch's healthd logged "Enqueuing
  authorization request for dev.ycode.hs", "Marking health as in use:
  Authorization status changed for source 2", "prompting for
  authorization", and the card was presented by Carousel's HealthKit
  authorization alert (`com.apple.healthkit.AuthorizationAlert`). The
  store already had a **local source** (bundle `dev.ycode.hs`, provenance
  0, `local_device` 0) with **7 rows: status 100, request 203, mode 0,
  provenance 0**, `modification_epoch` 0, `deleted_object_anchor` 2.
- Card path: Review → "Allow Write Access" (toggle "All Requested Data
  Below") → Next → "Allow Read Access" (same toggle) → Continue → "How much
  historical data do you want to share" (Past 30 Days … Full History) →
  Done. Nothing was written until **Done**; then the 7 rows became
  **status 101**, request 203, mode 0, `date_modified` the time of Done,
  `modification_epoch` 1, `deleted_object_anchor` 3, `object_limit_anchor`
  0 and `object_limit_modified` null (Full History chosen). The app's
  completion came at Done (`success` 1), status API 2.
- A second request for all types wrote 192 new rows at once (166 shareable
  100/203, 26 read-only 100/202). Closing the card with ✕ set all 192 to
  **104** (request unchanged, epoch 1); the app's completion `success` 1.
- Offline answers on a shut-down watch: the 7 rows set back to 100 → the
  next launch's request status 1 (should request), status 0. Set to **101**
  (with `date_modified`) → request status 2, `requestAuthorization`
  completed in 8 ms **with no card**, status 2.
- **Phone rows present** (fresh identity `dev.ycode.hs3`): the phone app's
  request wrote 7 rows 100/203 on the phone; 1 min later the watch had a
  second source for the same bundle (provenance 1, the phone's sync
  identity) with those 7 rows (provenance 1). The watch app's own request
  then still created **its own local source and 7 rows 100/203**, and the
  card showed. With the synced rows set to 101 and the local ones left at
  100 (watch shut down, then booted), the request status was 1 and the card
  showed again: **the watch's local rows decide**.
- The watch's local grant had not reached the phone after 2 min (watch →
  phone rows travel like samples, below).
- No non-GUI grant exists in the reference: `simctl privacy` 27.1 lists no
  Health service; `devicectl` has no health command; no defaults key was
  looked for beyond that (level 5 not justified, the store edit works).

## Q5 (health open question 11): watch samples at rest reaching the phone (level 3)

Watch app writes 4 samples (steps, heart rate, SpO₂, sleep) at rest; counts
read from copies of the phone's `healthdb_secure.sqlite` (samples whose
provenance has `sync_provenance` 1).

| Phone event | Result |
|---|---|
| nothing, 2 min 15 s | not on the phone |
| our non-HealthKit app (WCP2) brought to the foreground | nothing in 45 s (the step that sent HealthSim to the background, below) |
| a HealthKit app that has only asked for authorization (`dev.ycode.hs3`), launched to the foreground | nothing in 40 s; healthd logged no process state for it |
| Settings brought to the foreground | nothing in 20 s |
| HealthSim launched with observer + anchored queries | healthd: "Registering observer <query manager> for process state changes for dev.ycode.hs", "Process dev.ycode.hs … state changed BKSApplicationStateUnknown -> BKSApplicationStateForegroundRunning … foreground 0 -> 1", "syncing immediately with reason "client process entered foreground" options:'pull request'"; samples on the phone **≤ 3.7 s** later |
| HealthSim sent to the background (state → BackgroundRunning → BackgroundTaskSuspended), 4 new watch samples, 45 s | nothing |
| HealthSim back to the foreground (BackgroundTaskSuspended → ForegroundRunning) | pull at once; samples ≤ 5.3 s later |
| HealthSim terminated, relaunched with no query (Terminated → ForegroundRunning) | pull at once (the bundle stays registered in healthd) |

The pull on the wire (`health.sync.classc`, IDS message id **2**): the phone
sends one "Changes" request (826 B) whose session status is Finished with no
changes and status ChangesRequested; the watch's healthd logs "syncing
immediately with reason "Remote requested sync" options:'requested by
remote'", runs a 40 ms session and sends its changes as four Changes
requests (438–743 B, id 2) about 1.4 s after the pull left the phone
(ids_simd's link delay); the phone applies them and answers each. The
phone's healthd on the first boot after the SimLaunchHost incident was not
ready for 4–5 min under load; the two runs with no effect before 01:22
were repeated after "daemon ready" and are not counted.

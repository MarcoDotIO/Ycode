# StoreKit observations (KIT-STOREKIT, 2026-10-19/20)

Dirty-side notes in prose for `specs/frameworks/storekit/`. No Apple code;
raw logs and dumps stay in `research/dirty/storekit/` (git-ignored).

## Setup

- Device: `ycode-test-storekit-1`, iPhone Duo, iOS 27.1 runtime 24A94401,
  created for this work (the only device touched).
- App: our StoreProbe (`research/experiments/storekit/StoreProbe`), built
  with `build.sh` (plain `swiftc`, ad-hoc signed, no team) and, for the
  scheme experiments, as an Xcode project generated by `make_project.py`
  (built by Xcode 27.1 and by `xcodebuild`).
- Each phase ran as one launch through `run.sh` (`simctl launch` with
  `--stderr`, `DYLD_FRAMEWORK_PATH` set to the platform frameworks so
  StoreKitTest finds XCTest). Reports, JWS files and screenshots were saved
  per phase. Sheets that needed taps were answered by taps in the first
  session (2026-10-19; how the taps were made is not recorded).
- A device log stream filtered to StoreKit subsystems and `storekitd`
  recorded daemon activity during the 2026-10-19 runs.

## Order of runs (2026-10-19)

env without session → products (first session on the device: empty
catalog, the device signing identity created at that moment) → products
again (7 products) → buy → env/relaunch without session and the second
bundle → sub (rate 1004, 45 s wait, crossgrade, downgrade, other group,
auto-renew off/on, price-increase calls, force renewal, expire, billing
retry) → refund → ask → fail (stopped at the first alert) → offers → sk1 →
fail again (alerts answered) → offers again → ui buy / refund / manage /
redeem with dialogs on.

Ids continued across phases (0 → 33) because `clearTransactions` does not
reset the counter. Some phases therefore start with transactions left by the
previous phase (e.g. unfinished renewals replayed through
`Transaction.updates` at launch).

## 2026-10-20

- The redeem sheet opened the evening before was still on screen after the
  app had been terminated and even uninstalled; `xcodebuild test` then hung
  before running tests. A device reboot cleared the sheet.
- The host was extremely loaded (load average 300–700, other agents'
  simulators and builds). Launches from Xcode took minutes; one
  `xcodebuild test` attempt hung after the build. Timing statements in the
  spec come from the 2026-10-19 session unless stated.
- Uninstalling the app removed its `Octane/<bundle id>` folder and its
  transaction rows, but kept its overrides row and the device signing
  identity.
- Xcode, scripted through its AppleScript dictionary (open the generated
  project, choose `ycode-test-storekit-1` as run destination, run), installed
  the scheme's configuration on the device: the daemon's copy appeared with
  `appName` = "StoreProbe" and a later plain launch without a session listed
  all 7 products. Under the host load the timing of the installation relative
  to the Run command was not clear-cut; the negative control (a scheme path
  one level shorter) and a repeat with the correct path were inconclusive
  because the launch took longer than the observation window.
- The JWS signing certificate and the StoreKit 1 receipt signer are
  different: the first is per device (created at the first session), the
  second is the fixed certificate that Xcode's StoreKit editor bundle also
  ships as its exportable test certificate (same SHA-256 fingerprint).

## Anomalies worth re-checking

1. Ask-to-Buy decline delivered the declined consumable as a verified
   transaction.
2. `expireSubscription` on the weekly product also produced an extra
   transaction in state failed with a purchase issue whose purchase date
   equals the previous renewal's.
3. `invalidDeviceVerification` simulated error: the purchase returned the
   previous transaction (same id) as verified.
4. Two subscriptions of the same group (monthly, and lite bought with the
   off-device test API backdated) were both current entitlements.
5. StoreKit 1 restore produced new transactions that StoreKit 2 reports with
   reason RENEWAL for a non-consumable.

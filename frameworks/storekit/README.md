# ycode-storekit — open StoreKit Testing

A clean-room, Linux-buildable reimplementation of StoreKit's local test store
("StoreKit Testing"), written only from `specs/frameworks/storekit/` under the
protocol in `AGENTS.md`. Package `ycode-storekit`. It contains no Apple code,
resources, certificates or keys: every signing identity is generated by Ycode
(per device), and the tests generate their own test CAs.

```
swift build && swift test          # macOS and Linux, Swift 6.4
```

```swift
import StoreKit        // this package's module
import StoreKitTest

let session = try SKTestSession(contentsOf: url)      // installs the configuration for this app
session.timeRate = .oneRenewalEveryTenSeconds
let products = try await Product.products(for: ["dev.ycode.skprobe.plus.monthly"])
if case .success(.verified(let transaction)) = try await products[0].purchase() {
    await transaction.finish()
}
```

## The module names on macOS

`StoreKit` and `StoreKitTest` carry the Apple framework module names
(interop identifiers). Inside this package's build SwiftPM's module search
path takes precedence over the SDK, so `import StoreKit` resolves to this
package; do not add it to a target that also needs Apple's StoreKit. The
configuration model's product type is `ConfiguredProduct` so that it does not
collide with `StoreKit.Product` when both modules are imported.

## Ycode-specific API

- `YcodeStoreKit` (StoreKit module): the process's runtime — the
  `StoreDevice`, bundle id, vendor id (`AppStore.deviceVerificationID`), app
  version, the device's JWS and receipt identities, the receipt location
  (`appStoreReceiptURL`), the StoreKit 1 callback queue, and two hooks:
  `confirmPurchase` (Ycode's purchase sheet; returns false to cancel; the
  default confirms) and `presentAlert` (shown alerts are also kept in
  `alerts`). `YcodeStoreKit.shared` is built from `YCODE_STOREKIT_DIRECTORY`,
  `YCODE_STOREKIT_BUNDLE_ID` and `YCODE_STOREKIT_APP_VERSION`;
  `YcodeStoreKit.configure(_:)` replaces it.
- `Transaction.ycodeRequestRefund(developerIssue:)`: the refund request
  without a sheet (the sheet's two choices map to revocation reasons 1 and 0).
- `SKTestError.ycodeObservedError`: the reference's error form for parity checks.
- `SKPaymentQueue.ycodeReset()`: a fresh default queue after replacing the runtime.
- Engine: `StoreDevice(clock:timeZone:directory:quirks:)`, `ManualClock`,
  `AppTestStore` (every store and control operation, `advance()`,
  `nextEventDate()`, observers), `EngineQuirks` (`.reference` keeps two
  reference behaviors that look like bugs; `.none` drops them),
  `StoreDevice.promotionalOfferVerifier` and
  `PromotionalOfferSignature.verifier(keys:)`.

## Behavior notes and deviations

1. **No daemon.** The engine is an in-process library; persistence is JSON
   files per app under `<directory>/<bundle id>/` (`Configuration.storekit`,
   the store's copy with `appName`; `store.json`; `overrides.json`, which
   survives `uninstall()`), not SQLite (`design.md` §4 item 7). Signing
   identities live in `<directory>/_signing/`.
2. **Receipt identity per device.** The reference signs receipts with one
   fixed certificate (2020-04-01 to 2040-03-27); Ycode generates its own per
   device with the same subject and validity, so nothing is shipped.
3. **Headless UI.** The scene-based calls (`purchase(confirmIn:)`,
   `beginRefundRequest(in:)`, `showManageSubscriptions`,
   `presentOfferCodeRedeemSheet`, `requestReview`) are not provided; the
   hooks above stand in for Ycode's sheets. StoreKit 1 payments show no
   confirmation.
4. **Errors of the control API** are the documented `SKTestErrorDomain` codes
   (`errors.md` §3); the observed form is available as described.
5. **Off-device purchases** (`buyProduct`) always succeed (open question 2 of
   `testing-session.md`).
6. **`Transaction.updates`** replays the unfinished transactions at the start
   of every new sequence (the reference does it once per launch).
7. **Verification simulations:** `invalidSignature` produces a signature that
   really fails; `invalidCertificateChain`, `invalidEncoding` and
   `missingRequiredProperties` mark the result unverified;
   `revokedCertificate` and `invalidDeviceVerification` leave it verified, as
   observed.
8. **`_storeKitErrors`** in a file is kept but not applied (its element
   structure is unknown); simulated errors come from the API.
9. **Signed promotional offers** are checked with keys the caller supplies
   (`PromotionalOfferSignature.verifier(keys:)`), using the publicly documented
   signature payload; without keys every signature is rejected, as on the
   reference without the configuration's key.
10. **Locale matching** is exact (`en_US` vs `en-US` treated alike); `en` does
    not match `en_US`.
11. **New files** are written without a trailing newline and with `/` escaped
    as `\/` (the Foundation writer's defaults); a file read from disk keeps
    its trailing newline. Strings written with other escapes (`é`) are
    normalized on write.

## Spec questions found while implementing

1. `configuration-file.md` §1: does Xcode escape `/` as `\/`, end the file with
   a newline, and write an empty object as `{`, blank line, `}`? Ycode assumes
   yes, no, yes.
2. §1: the key order of Foundation's sorted output for keys that differ only
   in case or start with `_`; Ycode sorts by UTF-16 code units.
3. §5: are subscription periods other than `P3D`, `P1W`, `P1M`, `P2M`, `P3M`,
   `P6M`, `P1Y` possible? Ycode accepts any single-unit duration and warns.
4. `testing-session.md` §2.1: how do the 10-series rates scale weeks, days and
   years? Ycode: a year is 12 months, a week 7/30 of a month, a day 1/30. The
   deprecated series use a 7-day week, 30-day month, 365-day year.
5. Storefront numeric ids and currencies other than USA (Ycode uses the
   published App Store storefront ids) and what an unknown storefront code
   gives (Ycode: empty id, currency `XXX`).
6. `formats.md` §2.2 `offerPeriod` of a pay-as-you-go offer: the whole
   duration (Ycode, `P3M` for 3 × `P1M`) or one period?
7. `testing-session.md` §3.2 / §12 q4: the billing-retry window. Ycode: one
   period of the product; with grace, a grace period of one period followed by
   one period of retry (state 3), then expiry with intent 2.
8. `formats.md` §2.1: the subject-alternative-name value, the order of the
   name attributes, the basic-constraints value and the serial-number form of
   the device certificate. Ycode: DNS `storekit-testing.invalid`, CN then O,
   `cA` absent, 16 random bytes; key usage digitalSignature only.
9. `testing-session.md` §2 `expireSubscription`: the renewal info afterwards.
   Ycode: state 2, auto-renew 0, expiration intent 2 (like a failed renewal),
   plus the observed failed transaction with a purchase issue.
10. §7: the expiration intent of a refunded subscription ("an
    `expirationIntent`"). Ycode: 1.
11. §3.1: a crossgrade to the same level with the same duration — immediate
    (public documentation, Ycode's choice) or at the next renewal?
12. §5 item 4: are offer codes looked up in the purchased product only (Ycode)
    or across its group? How do `new`/`existing`/`expired` apply to a code
    redeemed at purchase time?
13. §6: after an approval, is the purchase date the request time or the
    approval time (Ycode: approval), and is the id kept (Ycode: yes)?
14. §3.1 last row: the backdated catch-up renewal reported `isUpgraded` —
    Ycode marks a renewal upgraded when a higher level of the group is
    entitled at processing time and ends that subscription.
15. `formats.md` §3: is attribute 1719 present (0/1) for every auto-renewable
    entry (Ycode) or only when 1? Are restored transactions listed? Ycode
    writes attributes in type order, not in DER SET order.
16. `formats.md` §2.4: does the app transaction carry `signedDate` or
    `environment`? Ycode follows the table (neither; `receiptType` instead).
17. `formats.md` §2.3: is `isInBillingRetryPeriod` always present (Ycode) or
    only when true?
18. `Transaction.webOrderLineItemID` type (Ycode: `String?`), and the Swift
    signature of `SKTestSession.buyProduct(identifier:options:)` (Ycode returns
    the `Transaction`).
